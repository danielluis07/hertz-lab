# Modules

What a module *is* — one owner of one coherent slice of behaviour behind one
public surface — is settled by ADR-0008, along with the thirteen of them and
their names. What sits *above* them is settled by ADR-0007. This file is the
inside: the folders a module has, what may be imported from outside it, and
where its types and schemas live.

Which way a dependency between two modules may point is ADR-0009.

## Anatomy

```
modules/products/
  schemas.ts            # Zod — the entity's vocabulary
  types.ts              # only what has no inference source
  constants.ts          # module-owned values
  <concept>.ts          # pure rules, named by concept: pricing.ts, stock.ts
  components/           # used by both audiences
  hooks/                # used by both audiences
  server/               # the module's server half
  admin/
    components/
    hooks/
  shop/
    components/
    hooks/
```

**Nothing here is a scaffold.** Every file and folder appears when something
needs it and not before. A module with three pure rules and one form is three
files and a folder; creating the other seven empty is how a convention becomes
ceremony.

Four rules give the layout:

**1. The entity's own vocabulary lives at the module root.** Schemas, types,
constants and pure rules are the same for everyone who speaks about a Product.
Audience folders hold only what one audience uses. This is ADR-0008's rule 3
made concrete: it is what keeps `productSchema` in one place while an admin
table and a shop grid stay apart.

**2. Audience folders exist only where both audiences do.** `products`,
`brands`, `categories`, `coupons`, `orders`, `customers` and `reviews` get
`admin/` and `shop/`. `checkout`, `cart`, `wishlist`, `payments`,
`shipping-methods` and `auth` serve one audience each and get **no** audience
folder at all — `modules/checkout/components/`, never
`modules/checkout/shop/components/`. A folder that would always be the same
single value is noise.

**3. `components/`, not `ui/`.** `components/ui/` already means one specific
thing in this repo: files generated by the shadcn CLI, which will overwrite
them. Reusing the word inside a module would suggest a relationship that does
not exist.

**4. Pure rules are named by concept, not by category.** `pricing.ts`,
`stock.ts`, `status.ts` — not `utils.ts`, `helpers.ts` or `lib.ts`. A module
that mirrors the global layer's folder names inside itself has just built
thirteen junk drawers, which is the failure ADR-0007 was written to avoid.

`server/` holds the module's server half; what is inside it is specified
separately.

## The public surface

**There is no barrel.** Callers deep-import, and the folder layout is the API.

ADR-0007 gutted `lib/utils/index.ts` for bundle reasons, and those reasons are
stronger here. A `modules/products/index.ts` re-exporting the admin form, the
shop grid and the server router would either drag `import "server-only"` code
into a client bundle and fail the build, or ship the whole module to every
consumer that wanted one component.

So the surface is a rule rather than a file:

| Path | Importable by |
| --- | --- |
| `modules/<name>/*` (root files) | any module, any route |
| `modules/<name>/<audience>/*` | routes of that audience, and the module itself |
| `modules/<name>/server/*` | the module's own server code, and `trpc/routers/_app.ts` composing it |

The `server/` line is the one that matters, and it is **enforced**, not merely
documented: a `no-restricted-imports` rule fails the import at lint time. Left
to convention it fails at build time instead, with a `server-only` error that
names the leaf file and not the import that dragged it in.

Everything else is convention. The audience line is worth stating and not worth
enforcing — importing `products/admin/` from a shop route is a mistake that
reads as one.

## Types

**Infer by default. Hand-write only what has no source.**

A module does not re-export raw Drizzle rows. `typeof products.$inferSelect` is
the shape of a table, and what a caller actually receives is the shape of a
procedure's return — so the exported type is
`RouterOutput["products"]["list"][number]`. Types that track the storage rather
than the surface go stale silently the first time a procedure selects a subset.

Form values come from Zod: `z.infer<typeof productSchema>`.

`types.ts` is for what genuinely has no inference source — a discriminated union
of UI state, a status the database stores as text. It exists only when there is
something to put in it.

**There is no root `types/` folder.** A folder named for a category of thing,
rather than an owner of behaviour, is exactly what ADR-0008 decided against.
`types/auth.ts` splits along ADR-0007's line: `Session` and `UserRole` are
*shapes* and stay with the global Better Auth infrastructure; `ErrorTypes`,
which maps Better Auth's error codes to pt-BR copy, is a *rule* and belongs to
`modules/auth/`.

## Schemas

**One `schemas.ts` at the module root**, serving both the tRPC procedure input
and the React Hook Form resolver. One schema, one place — the same reason
`lib/utils/document.ts` keeps `documentSchema` next to the formatter and the
validator for the value it describes.

Schemas only one audience speaks live in that audience's folder. An admin list's
filter schema is an admin concern; a Product is not.

## Promotion

ADR-0007's tie-breaker — **promote on the second caller, never on the first** —
extends from `lib/` to `components/` and `hooks/`, with a stricter gate.

A component promotes out of a module into the global `components/` only when a
second **module** needs it **and** it knows no rule. Both halves are required.
Two modules wanting a `ProductCard` is not a promotion: that component knows
product rules, and it belongs to `products` no matter how many callers it has.

`components/pagination-nav.tsx` is the shape to copy. It takes `paramKey` as a
prop precisely so that it knows no rule — ADR-0005 gives public routes `pagina`
and admin routes `page`, and a component that hard-coded either would have been
a module's component wearing a global's clothes.

The same rule runs one level down: a component used by both `admin/` and
`shop/` moves up to the module root; one used by a single audience stays put,
however tempting the symmetry.
