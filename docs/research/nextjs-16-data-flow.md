## 1. `params` and `searchParams`, and where `PageProps` comes from

### Where the global type comes from

`PageProps` is **generated**, not imported. `01-app/03-api-reference/05-config/02-typescript.md`
("Route-Aware Type Helpers"):

> Next.js generates global helpers for App Router route types. These are available without
> imports and are generated during `next dev`, `next build`, or via `next typegen`:
> `PageProps`, `LayoutProps`, `RouteContext`.

`01-app/03-api-reference/03-file-conventions/page.md` ("Page Props Helper") repeats it:
types are generated during `next dev`, `next build`, or `next typegen`, and after
generation the helper is globally available and does not need to be imported.

In this repo the generated declaration lives at **`.next/dev/types/routes.d.ts`** (written
by `next dev`) and **`.next/types/routes.d.ts`** (written by `next build`). `tsconfig.json`
pulls both in via `include`: `".next/types/**/*.ts"` and `".next/dev/types/**/*.ts"`.
`next-env.d.ts` additionally imports `./.next/dev/types/routes.d.ts` directly.

The generated text (identical in both files, `.next/dev/types/routes.d.ts:79-82`):

```ts
declare global {
  interface PageProps<AppRoute extends AppRoutes> {
    params: Promise<ParamMap[AppRoute]>
    searchParams: Promise<Record<string, string | string[] | undefined>>
  }
}
```

`ParamMap` is generated from the real route tree; the same file lists every route in this
app, and `"/admin/orders/[id]": { "id": string; }`. This is why
`app/(admin)/admin/orders/[id]/page.tsx` can write `PageProps<"/admin/orders/[id]">` with
no import and get `{ id: string }` back from `await params`.

**Consequence to note:** the generated types are build artifacts. A checkout that has never
run `next dev`, `next build`, or `next typegen` will not typecheck a page that uses
`PageProps`. `02-typescript.md` confirms `next-env.d.ts` is likewise regenerated by those
commands and should be gitignored, not edited.

### The contract for `params`

`03-file-conventions/page.md`: `params` is "a promise that resolves to an object containing
the dynamic route parameters from the root segment down to that page." Shape table from the
same file:

| Example route | URL | `params` |
| --- | --- | --- |
| `app/shop/[slug]/page.js` | `/shop/1` | `Promise<{ slug: '1' }>` |
| `app/shop/[category]/[item]/page.js` | `/shop/1/2` | `Promise<{ category: '1', item: '2' }>` |
| `app/shop/[...slug]/page.js` | `/shop/1/2` | `Promise<{ slug: ['1', '2'] }>` |

Static routes resolve `params` to `{}` (`page.md`, "Page Props Helper" good-to-know).

### The contract for `searchParams`

`03-file-conventions/page.md`:

- A promise resolving to `Record<string, string | string[] | undefined>`. `?a=1` gives
  `{ a: '1' }`; `?a=1&a=2` gives `{ a: ['1', '2'] }`.
- It is "a plain JavaScript object, **not** a `URLSearchParams` instance."
- **It is a Request-time API.** "Using it will opt the page into dynamic rendering at
  request time."
- Layouts do **not** receive `searchParams`
  (`03-api-reference/04-functions/use-search-params.md`, "Layouts"), because a shared layout
  is not re-rendered during navigation and the value would go stale.

**Asymmetry worth knowing:** the generated `PageProps` types `params` per route from
`ParamMap`, but `searchParams` is the same untyped `Record<string, string | string[] |
undefined>` for **every** route. Route-literal typing buys nothing for query parameters. Any
per-module vocabulary (ADR-0005: English in admin, Portuguese on the shop) has to be
validated at runtime — the framework will not type it. This repo already has the shape for
that in `normalizeProductsParams` in `data-flow.tsx`.

Both props are declared non-optional in the generated interface, though the docs describe
them as optional props; a page that does not need `searchParams` simply never destructures
it.

### Synchronous access is gone

`02-guides/upgrading/version-16.md` ("Async Request APIs (Breaking change)"):

> Version 15 introduced Async Request APIs as a breaking change, with **temporary**
> synchronous compatibility. Starting with **Next.js 16**, synchronous access is fully
> removed.

The removal covers `cookies`, `headers`, `draftMode`, `params` in `layout.js`/`page.js`/
`route.js`/`default.js` and the metadata image files, and `searchParams` in `page.js`. Any
recollection of a synchronous `params` object is wrong for this version.

## 2. Caching and rendering defaults

### `use cache` is not available in this project

`03-api-reference/01-directives/use-cache.md`: "`use cache` is a Cache Components feature.
To enable it, add the `cacheComponents` option to your `next.config.ts` file."
`05-config/01-next-config-js/cacheComponents.md` confirms `cacheComponents` gates
`use cache`, `cacheLife`, and `cacheTag`, and was introduced in 16.0.0.

`next.config.ts` in this repo does not set it. **So `use cache`, `cacheLife` and
`cacheTag` are all unavailable here today**, and the applicable caching model is the one in
`02-guides/caching-without-cache-components.md`, which opens: "This guide assumes you are
**not** using Cache Components."

Enabling it later is not free. `version-16.md` (`experimental.dynamicIO` and
`experimental.useCache`): "Enabling `cacheComponents` is not a rename-only change: it can
surface build errors for uncached data outside of `<Suspense>` and requires adopting the
Cache Components model." `cacheComponents.md` adds that it makes **Partial Prerendering the
default** and switches client navigation to React `<Activity>`, preserving component state
across route changes instead of unmounting.

### What is cached by default, without Cache Components

- **`fetch` is not cached by default.** `caching-without-cache-components.md`: "By default,
  `fetch` requests are not cached. You can cache individual requests by setting the `cache`
  option to `'force-cache'`." (This is the opposite of the Next 13/14 default that
  training data remembers.)
- **Route Handlers are not cached by default.** `01-getting-started/15-route-handlers.md`,
  "Caching": "Route Handlers are not cached by default. You can, however, opt into caching
  for `GET` methods... Other supported HTTP methods are **not** cached." So
  `app/api/trpc/[trpc]` and `app/api/auth/[...all]` are uncached, correctly.
- **Prerendering is the default for components that do not use Request-time APIs.**
  Glossary (`01-app/04-glossary.md`, "Prerendering"): "Prerendering is the default for
  components that don't use Request-time APIs."
- **Non-`fetch` work is cached only if you ask.** `caching-without-cache-components.md`
  points at `unstable_cache` for that, but
  `03-api-reference/04-functions/unstable_cache.md` now carries a note: "This API has been
  replaced by `use cache` in Next.js 16. We recommend opting into Cache Components and
  replacing `unstable_cache` with the `use cache` directive." Since Cache Components is off
  here, this repo currently has **no non-deprecated way to cache a Drizzle query across
  requests** — only React `cache` for per-request memoization.

### What opts a route into dynamic rendering

Glossary, "Request-time APIs" — using any of these makes the component dynamic:

- `cookies()`
- `headers()`
- `searchParams` (the page prop)
- `draftMode()`

Plus, from `caching-without-cache-components.md` ("Route segment config"):
`export const dynamic = 'force-dynamic'`, `export const revalidate = 0`, or any uncached
fetch. And `04-functions/connection.md`: `await connection()` "indicates rendering should
wait for an incoming user request before continuing" — the recommended explicit opt-in when
a component produces per-request output without touching a Request-time API.
`use-search-params.md` notes the preference directly: "Previously, setting
`export const dynamic = 'force-dynamic'` on the page was used to force dynamic rendering.
Prefer using `connection()` instead."

**Applied to this repo — this is load-bearing for #8:** `lib/auth-utils.ts` calls
`headers()` inside `getCurrentSession`, and ADR-0006 requires every protected `page.tsx` to
call `requireAdmin()` / `requireAuth()`. `headers.md` states that using it "will opt a route
into dynamic rendering." **Every admin page and every account page in this app is therefore
already dynamically rendered at request time, before any data-fetching decision is made.**
There is nothing static about the admin surface to preserve, and no static/dynamic
trade-off to weigh in choosing a fetching path there.

### Revalidation, if it is ever needed

`version-16.md`, "Caching APIs":

- `revalidateTag` **now requires a second argument**, a `cacheLife` profile:
  `revalidateTag('posts', 'max')`. "The single-argument form is deprecated and will produce
  a TypeScript error." Any remembered one-argument call is now wrong.
- `updateTag(tag)` is **new in 16** and **Server-Actions-only**. It gives read-your-writes:
  it expires and immediately refreshes within the same request.
- `refresh()` from `next/cache` is **new in 16** and, per
  `04-functions/refresh.md`, "can **only** be called from within Server Actions. It cannot
  be used in Route Handlers, Client Components, or any other context."
- `cacheLife` and `cacheTag` lost their `unstable_` prefixes (but still need
  `cacheComponents`).

## 3. Prerendering and `useSearchParams` — is the hook's comment right?

`hooks/use-query-param.ts` carries this warning:

> Any component calling this needs a `<Suspense>` boundary above it on a prerendered route,
> or the production build fails — `useSearchParams` opts the tree below it out of
> prerendering.

**The rule holds in 16.3.4, and the comment's qualifier "on a prerendered route" is exactly
the right one.** From `03-api-reference/04-functions/use-search-params.md`, "Behavior":

> **Prerendering.** If a route is prerendered, calling `useSearchParams` will cause the
> Client Component tree up to the closest `Suspense` boundary to be client-side rendered.

and, in the same section's good-to-know:

> - In development, routes are rendered on-demand, so `useSearchParams` doesn't suspend and
>   things may appear to work without `Suspense`.
> - During production builds, **a static page** that calls `useSearchParams` from a Client
>   Component must be wrapped in a `Suspense` boundary, otherwise the build fails with the
>   *Missing Suspense boundary with useSearchParams* error.

So, stated precisely:

1. The failure is a **production build** failure (`next build`). `next dev` renders
   on demand and will not reproduce it. A page can look fine locally and break CI.
2. It fires only on a **statically prerendered** route. `use-search-params.md`,
   "Dynamic Rendering": "If a route is dynamically rendered, `useSearchParams` will be
   available on the server during the initial server render of the Client Component."
3. The boundary must be **above** the calling client component. The doc's phrasing is that
   the client tree "up to the closest `Suspense` boundary" gets client-side rendered — the
   boundary sets the ceiling on what is dropped from the prerender, so everything above it
   still prerenders. (The hook's own wording, "opts the tree below it out of prerendering",
   describes the same effect from the other end and is close enough not to mislead.)
4. If a route is meant to be dynamic anyway, the doc's preferred escape is `await
   connection()` in a Server Component "first ... this excludes everything below from
   prerendering", rather than adding a boundary purely to satisfy the build.

**Applied to this repo:** because `requireAdmin()` calls `headers()` (see §2), admin routes
are dynamic and **the build failure cannot fire there**; `useQueryParam` can be called on an
admin page with no `<Suspense>` above it and `next build` will pass. The hook is global and
also serves shop routes, where the rule bites hard — a shop listing page with no
Request-time API is prerendered, and an unwrapped `useQueryParam` fails the build. The
comment is correct as a global rule; it is simply not the reason an admin page would want a
boundary.

There is a related trap in the same family: `use-search-params.md` also notes that passing a
page's `searchParams` prop into a Client Component and unwrapping it with React's `use()`
"will suspend, so the Client Component should be wrapped with a `Suspense` boundary."

## 4. Streaming and Suspense with `useSuspenseQuery`

### What streams, mechanically

`02-guides/streaming.md`, "How the App Router delivers a page":

- **The HTML stream.** "The static parts of your page (layouts, navigation, Suspense
  fallbacks) render first and are sent immediately. When a `<Suspense>` boundary's content
  is ready ... React streams its completed HTML along with inline `<script>` tags: one that
  swaps the fallback DOM node with the new content, and another carrying the component
  payload." The swap happens "without waiting for the page's JavaScript bundle to load or
  hydration to complete."
- **The static shell** is "everything that renders before any async work resolves ... your
  layouts, navigation, and the fallback UI defined by your `<Suspense>` boundaries."
- "Each `<Suspense>` boundary is an independent streaming point. Components inside different
  boundaries resolve and stream in independently. They don't block each other."
- On **client-side navigation** no HTML is transferred at all — "only the component payload
  is fetched (with an `rsc: 1` request header)".

### The prefetch/hydrate/`useSuspenseQuery` triangle

Next ships a first-party guide for exactly the pattern in `data-flow.tsx`:
`02-guides/client-side-data-fetching/tanstack-query.md`. Its decision table
(`02-guides/client-side-data-fetching/index.md`, "Choose a client fetching pattern"):

| Pattern | TanStack Query | When data becomes available |
| --- | --- | --- |
| Inline loading states | `useQuery` | Browser request after hydration |
| Suspense loading states | `useSuspenseQuery` | Browser request after hydration |
| Provided by the server | `<HydrationBoundary>` | Initial render or streamed from server |

Facts from the TanStack guide that bear on `data-flow.tsx` and `trpc/server.tsx`:

- **Streaming a pending prefetch requires opting in.** "TanStack Query 5.40.0 or later can
  dehydrate pending queries. Start `prefetchQuery` without awaiting it, then pass the
  dehydrated state to `<HydrationBoundary>`" — with
  `shouldDehydrateQuery: (query) => defaultShouldDehydrateQuery(query) || query.state.status === 'pending'`.
  **This repo already does exactly that** in `trpc/query-client.ts`, and `prefetch()` in
  `trpc/server.tsx` deliberately does not await (`void queryClient.prefetchQuery(...)`). So
  path 1 in `data-flow.tsx` genuinely streams: the page does not block, the fallback is
  sent in the shell, and the resolved data arrives in the same response. Without the
  `shouldDehydrateQuery` override an unresolved prefetch would be dropped and the browser
  would refetch after hydration.
- **Errors reach the error boundary, not the Suspense boundary.** "If the initial request
  fails, `useSuspenseQuery` propagates the error to the nearest error boundary." This is
  why `data-flow.tsx` nests `<Suspense>` inside a boundary rather than beside it — the two
  are not interchangeable and the ordering matters.
- **The fallback shows once.** "After a query has data, later refetches for the same query
  keep the cached data rendered instead of showing the Suspense fallback again. Use
  `isFetching` to provide background refresh feedback." A skeleton is initial-load UI; a
  filter change on an already-loaded admin table will not re-show it.
- **Sibling boundaries, not sibling hooks.** "Multiple `useSuspenseQuery` calls in one
  component run sequentially. Put independent queries in sibling components, or use
  `useSuspenseQueries`." A detail panel that needs an order plus its customer will
  waterfall if both hooks sit in one component.
- **The server and client must share the query key.** "The server and Client Component must
  use the same query key. Keep the key and query options together so both call sites share
  the same identity." With `createTRPCOptionsProxy` the tRPC proxy supplies that identity
  on both sides, which is what makes `prefetch(trpc.x.queryOptions())` and
  `useSuspenseQuery(trpc.x.queryOptions())` line up.

### `loading.js` versus `<Suspense>`

`02-guides/streaming.md`, "When to use `loading.js` vs `<Suspense>`":

| | `loading.js` | `<Suspense>` |
| --- | --- | --- |
| Scope | Entire page | Any component |
| Navigation | Prefetched as instant fallback | Not prefetched by default |
| Best for | Pages where nothing renders without data | Most pages, for granular control |

The guide's own recommendation: "Prefer explicit `<Suspense>` boundaries close to the
dynamic access... A `loading.js` high in the tree is a valid boundary, so the framework
finds it and stops, but now the entire page falls back to a full-page skeleton instead of
streaming granularly."

`03-file-conventions/loading.md` fixes the nesting: `loading.js` "wraps `not-found.js`,
`page.js`, and nested `layout.js` files in a `<Suspense>` boundary. It does **not** wrap the
`layout.js`, `template.js`, or `error.js` in the same segment." Its fallback **is**
prefetched, which `<Suspense>` in a page is not.

### The HTTP contract, once streaming starts

`02-guides/streaming.md`, "The HTTP contract" — relevant to ADR-0006's page-level auth
checks:

> Once streaming begins, the HTTP response headers (including the status code) have already
> been sent to the client. **You cannot change the status code or headers after streaming
> starts.**

Concretely: "If a `notFound()` fires mid-stream, Next.js cannot go back and change the
status to 404. Instead, it injects `<meta name="robots" content="noindex">`... Similarly, a
`redirect()` mid-stream becomes a client-side redirect rather than an HTTP redirect header."
And: "The response body begins streaming when a Suspense fallback renders... or when a
component suspends under a `<Suspense>` boundary. To get a real HTTP status code for errors,
place `notFound()` **before** any `await` or `<Suspense>` boundary."

`requireAdmin()` redirects. For an unauthorized visitor to get a real HTTP redirect rather
than a client-side one, the `await requireAdmin()` must complete before anything suspends —
which is what `app/(admin)/admin/orders/[id]/page.tsx` already does by awaiting it on the
first line.

## 5. `error.tsx` versus an in-page error boundary

### What `error.tsx` catches

`03-api-reference/03-file-conventions/error.md`:

- "`error.js` wraps a route segment and its nested children in a React Error Boundary."
- In the component hierarchy it "wraps `loading.js`, `not-found.js`, `page.js`, and nested
  `layout.js` files in a React error boundary. **It does not wrap the `layout.js` or
  `template.js` above it in the same segment.** To handle errors in the root layout, use
  `global-error.js`."
- Errors bubble to the nearest parent boundary
  (`01-getting-started/10-error-handling.md`, "Nested error boundaries"), so the four
  `error.tsx` files in this repo (`app/`, `app/(admin)/`, `app/(shop)/`, `app/(account)/`)
  form a chain, each catching what the level below did not.
- Granularity is fixed at the **route segment**. It cannot scope to one panel of a page.
- Error boundaries "don't catch errors inside event handlers"; they catch errors during
  rendering (`10-error-handling.md`). But "unhandled errors inside `startTransition` from
  `useTransition` will bubble up to the nearest error boundary" — which matters, because
  `hooks/use-query-param.ts` navigates inside `startTransition`.
- Mid-stream, "the nearest `error.js` boundary catches it and renders the error UI in place
  of the failed component. The rest of the page remains intact" (`02-guides/streaming.md`).
- Message contents differ by side: "Errors forwarded from Client Components show the
  original `Error` message. Errors forwarded from Server Components show a generic message
  with an identifier" (`error.md`, `error.message`). A `TRPCError` thrown by a server caller
  will **not** reach the browser with its pt-BR message intact — only `error.digest`.

**Applied to this repo:** `app/(admin)/error.tsx` cannot catch a throw from
`app/(admin)/layout.tsx`. `ConfirmProvider` and `SidebarProvider` are mounted in that
layout, so a failure in either escapes to `app/error.tsx`.

### `retry` versus `reset` — a 16.3 change

`error.md` version history:

| Version | Change |
| --- | --- |
| `v16.3.0` | `retry` prop became stable. |
| `v16.2.0` | `unstable_retry` prop added. |

`retry()` "will try to re-fetch and re-render the error boundary's children." `reset()` is
still there, but the doc is explicit: "In most cases, you should use `retry()` instead.
However, if you have a specific reason to clear the error state and re-render the error
boundary's children **without re-fetching**, you can use the `reset()` function." And from
`04-functions/catchError.md`: `reset()` "won't recover from Server Component errors."

`app/(admin)/error.tsx` already takes `retry`, which is correct for 16.3.4 and would have
been wrong on any earlier version. Remembered `reset`-only signatures are stale.

### `catchError` — the framework's own in-page boundary

**New and directly relevant.** `03-api-reference/04-functions/catchError.md`:

> The `catchError` function creates a component that wraps its children in an error
> boundary. It provides a programmatic alternative to the `error.js` file convention,
> enabling **component-level error recovery anywhere in your component tree**.

Version history: `unstable_catchError` in 16.2.0, **stable in 16.3.0** — so it is available
in 16.3.4. It is imported from `next/error` and used as
`export default catchError(ErrorFallback)`.

The doc states three things a hand-rolled React error boundary does not give you:

> - **Built-in error recovery** — `retry()` re-renders the page inside a Transition,
>   preserving Client Components state outside of the error boundary.
> - **Framework-aware integration** — APIs like `redirect()` and `notFound()` work by
>   throwing special errors under the hood. `catchError` handles these seamlessly, **so
>   they're not accidentally caught by your error boundary**.
> - **Client navigation handling** — The error state automatically clears when you do a
>   client navigation to a different route.

And: "Unlike the `error.js` file convention which is scoped to route segments, `catchError`
can be used to wrap any part of your component tree."

That second bullet is the sharp one. `data-flow.tsx` uses `<ErrorBoundary>` from
`react-error-boundary` (a real dependency, `^6.1.4`). That is a plain React boundary with no
knowledge of Next's control-flow throws. `redirect()` and `notFound()` are implemented as
thrown sentinels; a generic boundary placed above a component that calls them will swallow
the navigation and render "Something went wrong" instead. In this app that is not
hypothetical — `requireAdmin()` calls `redirect()`, and product/order detail pages are the
natural place for `notFound()`.

The framework offers a second escape hatch for the same class of problem:
`03-api-reference/04-functions/unstable_rethrow.md` exists for re-throwing framework
errors caught by user code, and `catchError.md` closes with "You don't need to wrap
`error.js` default exports with `catchError`."

## 6. Server Actions versus route handlers, for the write path

The question in #13 is narrow: does the write path have an option beyond tRPC mutations?
**Yes — Server Actions are a real alternative, and they are the option Next's own docs
assume.** But they carry constraints tRPC-over-route-handler does not.

### What a Server Action is here

`01-getting-started/07-mutating-data.md`: a Server Function is an async function marked with
`'use server'`, callable from the client over the network. "Behind the scenes, actions use
the `POST` method, and only this HTTP method can invoke them."

### Constraints that differentiate the two

From `02-guides/server-actions.md`:

- **Sequential dispatch — the big one.** "Next.js dispatches Server Actions one at a time
  per client. If a user triggers three actions in quick succession, the second waits for the
  first to finish, then the third waits for the second." And explicitly: "do not rely on
  `Promise.all` to parallelize Server Actions from the client. If you need parallel work,
  do it inside a single Server Action, fetch in parallel from a Server Component, or use a
  Route Handler for non-mutation requests." tRPC mutations POST to
  `app/api/trpc/[trpc]`, an ordinary route handler, and are not serialised this way. Any
  admin surface doing per-row actions across a table (bulk archive, bulk moderate) hits this
  difference.
- **1MB body cap by default.** "Action requests are capped at 1MB by default. Configure
  `serverActions.bodySizeLimit` when accepting larger payloads." Relevant to the
  product-image upload flow the map lists as unspecified.
- **A single response carries data and UI.** "When a Server Action triggers an immediate
  revalidation, Next.js does the work inside one HTTP request: it runs the action, then
  re-renders the current route server-side. The response... contains both" the return value
  and a fresh RSC payload "which the client commits as a seeded navigation." This is the one
  thing tRPC mutations structurally cannot do — a tRPC mutation returns data only, and the
  server-rendered part of the page has to be refreshed separately.
- **Action IDs rotate across deploys.** "New deployments typically generate new IDs (Next.js
  rotates them at most every 14 days, even when the source is unchanged), so a client still
  running the previous build may invoke an action ID that no longer exists."
- **Security is the app's job either way.** "Server Functions are reachable via direct POST
  requests, not just through your application's UI. Always verify authentication and
  authorization inside every Server Function." And: "Render-time gating (only rendering a
  form on an authenticated page) is not a security boundary." Framework-level protections
  listed: Origin/Host CSRF check, the body cap, encrypted action IDs with dead-code
  elimination of unused actions, and closure-variable encryption (needing a stable
  `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` across instances when self-hosted). `adminProcedure`
  in `trpc/init.ts` is the equivalent check on the tRPC side and it already exists.

### Refreshing the server-rendered half after a write

Four distinct tools, and 16 changed the set. `02-guides/server-actions.md`, "Choosing a
cache update":

| API | What it does | Callable from |
| --- | --- | --- |
| `updateTag(tag)` | Immediate expiry; the route re-render in the action's own response waits for fresh data. Read-your-own-writes. | Server Actions only |
| `revalidateTag(tag, profile)` | Stale-while-revalidate. "The action's own re-render does **not** wait for the new data." | Server Actions, Route Handlers |
| `revalidatePath(path)` | Invalidate by URL path, "when one route is affected and tagging is overkill." | Server Actions, Route Handlers |
| `refresh()` (`next/cache`) | Refetch the current route's RSC payload without invalidating cached data. | **Server Actions only** (`04-functions/refresh.md`) |
| `router.refresh()` (`next/navigation`) | Client-side equivalent. | Client Components |

"When `updateTag`, `revalidatePath`, or `refresh` runs, Next.js re-renders the current route
server-side and includes a newly rendered RSC Payload in the action's response, so the page
reflects the change in the same roundtrip."

**Which of these a tRPC mutation can reach.** A tRPC mutation executes inside the
`app/api/trpc/[trpc]` Route Handler, not a Server Action, so the split is:

- `04-functions/revalidateTag.md`: "`revalidateTag` can be called in Server Functions and
  Route Handlers" — **available**. It "cannot be called in Client Components or Proxy."
- `04-functions/revalidatePath.md`: "can be called in Server Functions and Route Handlers"
  — **available**, with a caveat: "**Route Handlers**: Marks the path for revalidation. The
  revalidation is done on the next visit to the specified path."
- `updateTag` and `refresh()` — **not available**; both are Server-Actions-only.
- The documented substitute for `updateTag` outside an action, from `revalidateTag.md`:
  "When the invalidation comes from outside a Server Action, for example a webhook or
  another service calling a Route Handler, `updateTag` is not available. Pass
  `{ expire: 0 }` to expire the data immediately."

`router.refresh()` still exists and its contract is stated in
`04-functions/use-router.md`: "Refresh the current route. Making a new request to the
server, re-fetching data requests, and re-rendering Server Components. The client will merge
the updated React Server Component payload without losing unaffected client-side React (e.g.
`useState`) or browser state (e.g. scroll position). This clears the Client Cache for the
current route, but does **not** invalidate the server-side cache."

**Two independent caches, and a `router.refresh()` gap.** `router.refresh()` clears Next's
Client Cache. It has no effect on TanStack Query's cache — those are separate layers, as
`02-guides/client-side-data-fetching/index.md` sets out (Next.js server cache / Next.js
client cache / client data-fetching library, "independent freshness policies"). A write that
must update both a `useSuspenseQuery` list and a server-rendered count needs
`queryClient.invalidateQueries` **and** a router refresh; neither alone covers both.

The Client Cache itself (glossary, "Client Cache") stores RSC payloads for visited and
prefetched routes; "Pages are not cached by default but are reused during browser
back/forward navigation", and it is invalidated by `revalidateTag`, `revalidatePath`,
`updateTag`, `router.refresh`, `cookies.set`, or `cookies.delete`. Default staleness comes
from `staleTimes` (`05-config/01-next-config-js/staleTimes.md`, still experimental):
`dynamic` defaults to **0 seconds** (not cached) as of 15.0.0, `static` to 5 minutes. Admin
pages are dynamic, so a redirect-after-write to `/admin/products` will not serve a stale
cached page from the client cache — but it will re-run the server render, which is a real
request.

### Route handlers, for completeness

`01-getting-started/15-route-handlers.md`: `GET POST PUT PATCH DELETE HEAD OPTIONS`
supported, 405 otherwise; not cached by default; cannot coexist with a `page.js` at the same
segment; "they **do not** participate in layouts or client-side navigations like `page`."
Typed with the generated `RouteContext<'/api/...'>` global, the sibling of `PageProps`.

## What this changes for the open tickets

Flagged, not decided.

**For #8 (which fetching path, and who owns Suspense):**

1. Every admin page is already dynamically rendered, because ADR-0006 puts `requireAdmin()`
   → `headers()` in every `page.tsx`. Static-versus-dynamic is not an input to the path
   rule on the admin side. The "detached server `caller` ... for static rendering" comment
   in `data-flow.tsx` describes a mode the admin surface does not have.
2. `data-flow.tsx` uses `<ErrorBoundary>` from `react-error-boundary`, which is not
   framework-aware. Next 16.3 ships `catchError` from `next/error` for precisely this slot,
   and warns that a plain boundary will accidentally catch the control-flow throws behind
   `redirect()` and `notFound()`.
3. `app/(admin)/error.tsx` cannot catch throws from `app/(admin)/layout.tsx` — the segment's
   own layout sits outside its error boundary. That bounds what a route-level `error.tsx`
   can be asked to own.
4. The `<Suspense>` requirement above `useQueryParam` does not apply to admin routes, since
   they are dynamic. If a boundary goes above an admin filter bar it is for streaming or
   layout reasons, not to keep the build green.
5. The repo's `shouldDehydrateQuery` override in `trpc/query-client.ts` is what makes the
   fire-and-forget `prefetch()` actually stream rather than silently fall back to a
   post-hydration browser fetch. It is load-bearing, not boilerplate.
6. `loading.tsx` and an in-page `<Suspense>` are not equivalent: only the `loading.tsx`
   fallback is prefetched for instant navigation.
7. `lib/request-cache.ts` (referenced by a comment in `trpc/server.tsx`, does not exist):
   React `cache` is the documented tool for per-request memoization of non-`fetch` work, and
   is "scoped to the current request only". `lib/auth-utils.ts` already uses it. There is no
   Next-specific API this file would need to wrap.

**For #9 (the write path):**

1. Server Actions are a genuine alternative to tRPC mutations, and are the only way to get
   the write's result and a re-rendered server tree in one roundtrip.
2. But Server Actions are **dispatched one at a time per client**, and capped at 1MB. Both
   bite on admin surfaces — bulk row actions and image upload respectively.
3. `refresh()` from `next/cache` is Server-Action-only. A tRPC mutation runs in a Route
   Handler, so it can call `revalidateTag` and `revalidatePath` but **not** `refresh()` or
   `updateTag()`; the client-side `router.refresh()` is the equivalent of the former.
4. `router.refresh()` and `queryClient.invalidateQueries` invalidate **different caches**.
   Neither substitutes for the other when a page has both server-rendered content and a
   `useSuspenseQuery` list.
5. If any server-side caching is ever added, `revalidateTag` now needs a second argument,
   and `updateTag` is the read-your-writes option — but both are Server-Action-shaped, and
   `updateTag` is Server-Actions-only.
6. A `TRPCError` thrown on the server reaches an `error.tsx` with its message stripped and
   only `error.digest` intact. pt-BR error copy therefore cannot travel as a thrown server
   error message; it has to come back as mutation return data (or be mapped client-side from
   the code).
